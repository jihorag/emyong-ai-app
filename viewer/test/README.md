# test/ — 회귀 검증 하네스

구조를 옮기는 동안 **"기능이 안 바뀌었다"를 사람 눈이 아니라 스크립트가 판정**합니다.

```bash
npm run verify     # lint + build + smoke  ← 매 재설계 단계의 통과 기준
npm run smoke      # 검증만 (build는 이미 돼 있다고 가정)
npm run baseline   # 현재 상태를 새 기준선으로 저장
```

## 무엇을 판정하나

| | 항목 | 왜 |
|---|---|---|
| 1 | 화면 렌더 14곳 | 온보딩·홈·복습·노트·채팅·스제트·변형문제·오답노트·논술·플래너·설정이 뜨는가 |
| 2 | **localStorage 키** | 데이터 계층을 옮겨도 저장 스키마가 그대로인가 — 키가 하나라도 바뀌면 **기존 사용자의 학습 데이터가 유실**된다 |
| 3 | **AI 프롬프트 바이트 대조** | 프롬프트를 다른 파일로 옮겨도 조립 결과가 한 글자도 안 달라졌는가 |
| 4 | 콘솔 에러 | 0인가 |
| 5 | 대시보드 반응 | 학습 후 예측 점수·스트릭·시기가이드가 실제로 움직이는가 |

3번이 이 하네스의 핵심입니다. 프롬프트는 템플릿 리터럴이라 옮기는 과정에서 공백 하나만
어긋나도 AI 응답 품질이 달라지는데, 눈으로는 절대 못 잡습니다.

## 어떻게 도는가

`vite preview`로 **실제 빌드 산출물**을 띄우고 Chrome으로 온보딩부터 통과시킵니다.
개발 서버가 아니라 배포될 물건을 봅니다.

`/api/ai`는 [`mock-ai.mjs`](mock-ai.mjs)가 가로챕니다. 세 가지 이유입니다 —
로컬엔 서버리스 함수가 없고, 검증마다 API 비용이 나가면 안 되고, 무엇보다
**AI 응답이 매번 다르면 회귀 검증이 성립하지 않습니다.** 목은 요청의 `system`을
전부 기록하는데, 그 기록이 곧 3번의 스냅샷입니다.

## 파일

| | |
|---|---|
| `verify.mjs` | 진입점. preview 기동 → 구동 → 기준선 대조 → 종료 코드 |
| `drive.mjs` | 사용자 흐름 재현. "무엇을 관측할지"만 담당, 판정은 안 함 |
| `mock-ai.mjs` | `/api/ai` 목 + 프롬프트 기록 |
| `baseline/` | 기준선. **의도적으로 기능을 바꿨을 때만** 갱신 |

## 기준선을 갱신해도 되는 때

`npm run baseline`은 **기능을 의도적으로 바꿨을 때만** 씁니다.
구조 재설계 중에는 절대 쓰지 마세요 — 검증이 무의미해집니다.

갱신했다면 커밋 메시지에 **무엇이 왜 바뀌었는지** 반드시 적습니다.
프롬프트 기준선이 바뀌었다면 그건 AI 동작이 바뀐 것이고, 리뷰에서 별도로 확인받아야 합니다.

## 요구 사항

`playwright-core` + 로컬에 설치된 **Chrome**(`channel: 'chrome'`)을 씁니다.
브라우저를 따로 내려받지 않으려는 선택입니다. Chrome이 없는 환경(CI 등)에서는
`chromium` 설치 후 채널 지정을 바꿔야 합니다.
